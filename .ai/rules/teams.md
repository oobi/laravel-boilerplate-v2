# Teams

## Team invitations are two independent switches, decoupled from TeamCreationMode
TeamCreationMode owns only WHO may create a team: self-service | admin-only (config teams.creation). Whether invitations exist is separate — two independent booleans read via Concise\Teams\Support\InvitationPolicy: membersMayInvite() (config teams.invitations.members — owner/admins inviting from the team area) and adminsMayInvite() (teams.invitations.admins — system admins inviting from Admin › Teams). Gate every invitation surface on the matching switch, never on the creation mode: team nav item + ListInvitations route + PendingInvitations member branch use members; admin TeamInvitations route + tab + ShowTeam stat + PendingInvitations admin branch use admins; InviteMember picks the switch by whether the inviter is a system admin. Named modes (SaaS / invitation-only / backoffice) are just recipe presets over these switches — see docs/config-recipes.md — not enum cases.

## Components check one TeamAbility; system-admin authority lives in TeamPolicy::before()
Never write `Gate::allows(SystemPermission::MANAGE_TEAMS) || Gate::allows(TeamAbility::X, $team)` in a component. `TeamPolicy::before()` maps the five team system permissions to abilities — `view teams` (the read floor; it alone opens the admin teams pages, read-only) grants `view`/`viewMembers`/`viewSettings`; `manage teams` grants every ability EXCEPT the three `PRIMARY_OWNER_ONLY` ones; `delete teams` grants `delete`; `manage team ownership` grants `manageOwners`/`transferOwnership` — then denies non-members, then grants the primary owner the non-delegable acts. So a call site asks for exactly one TeamAbility and the policy is the whole truth. The admin pages' `mount()` authorizes `view teams`; every edit surface on them gates its own visibility with `->authorize()` on the specific permission (`deactivate teams` has no ability — the toggle checks it directly), and a child component that aborts for a non-manager (`ManageOwnership`, `ManageDomains`) is rendered only behind the matching `can…()` check, as the member-side Settings page does — otherwise the whole page 403s for a read-only or manage-only admin. The only direct `manage teams` checks are where the admin/member distinction IS the rule: the admin-only "Add member" action, the self-row exemption in `MembersTable::canActOn()`, and `PendingInvitations::canManage()` (which invitation switch governs the viewer is decided by who they are — `before()` grants `invite` to admins, so the admin switch must be asked first). Team roles are assigned on the membership pivot (`Membership::roles()`, table `team_user_role`), never through spatie's teams feature — `permission.teams` stays off, so a SystemPermission answers identically inside and outside a team route and there is no scope to pin.

## Team permission implications are applied when a role is written, never at check time
`TeamPermission::implies()` is the one definition of "manage carries view". It is applied at WRITE time — `Team::createRole()` stores `TeamPermission::withImplied($permissions)`, and the Roles form's `resolvePermissionsFromState()` closes the saved set the same way — so what spatie stores is the truth: `checkPermissionTo()` and the Gate always agree, and `Team::memberHasPermission()` asks for exactly one permission. Any new path that grants team permissions (an import, a command, an API) must call `withImplied()` too. Do not add implication resolution to a check: two answers to one question is the trap this avoids. Changing an implication later = a code change plus `php artisan bp:roles:sync-implications` with that deploy (additive, idempotent, every scope, `--dry-run` to preview); removing one needs no fix.

## Team sidebar mirrors the admin shell; secondary pages are tabs
The team-area sidebar is Dashboard (rendered directly by team-sidebar-nav.blade) + one collapsible "Management" NavGroup registered in TeamsServiceProvider::registerTeamNavigation(), holding just Members and Settings — same shape as core's AdminNav. The nav-group component draws the separator + section header, so don't add one manually. Invitations and Domains are NOT nav items: they're tabs beside their sibling (Invitations on the Members page, Domains on the Settings page), via partials livewire/team/partials/{members,settings}-tabs.blade.php, gated by the exact same policy check as their route/page (INVITE / MANAGE_DOMAINS + the feature switch). The Members/Settings pages drop the tab bar entirely when the sibling tab isn't available (lone tab = plain page); the Invitations/Domains pages always show 2 tabs since they're only reachable with the feature on. Nav item `active()` lists both sibling routes so the group stays highlighted on either tab. Tab links use team_route(), which emits host URLs when DomainPolicy::enabled() — so a full-page render of these tabbed pages can't be tested in a path-mode-booted app that toggles domains config at runtime; render them in TeamHostModeHttpTest (real host mode) instead, or drive the inner component directly. Sidebar nav labels are read once at boot; the render-time :members word now lives in the Members page description.
